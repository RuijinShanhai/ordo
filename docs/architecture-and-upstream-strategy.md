# Ordo 架构与上游策略

## 1. 决策范围与事实等级

本方案采用独立产品仓 + 保留上游历史的 Archify 引擎 fork + 产品适配层 + Agent 辅助升级。它是初始化设计基线，不是实现或验收证明。

**已有来源**：此前方案整理实际阅读了上游 `https://github.com/tt-a1i/archify.git` 动态 main 对应的 README、Schema 说明、Apache-2.0 LICENSE，记录其 CLI 生成 HTML 的路径及 Schema 对未知字段的严格限制。该阅读未锁定 SHA，本轮不将它升级为当前版本核验结论。

**设计建议**：以下模型、接口、目录、沙箱、安全控制、测试矩阵和升级台账均为拟议实现。示例不是 Archify 原生 Schema 或已发布 API。

**本次实施边界**：只归档 Markdown。组织 fork 创建受 API 认证阻断，未确认引擎仓存在；没有子模块或锁定集成，没有渲染/部署/独立验收。禁止用占位 SHA、空目录或手写 `.gitmodules` 冒充接入完成。

## 2. 产品边界与阅读场景

读者进入流程目录，搜索或选择某个固定版本，查看全局图；定位节点后阅读业务属性及关联文档，探索上下游、分支及路径，并可回到全局。路径探索表达模型关系，不保证业务上可执行；条件不明、循环及不可达节点应显式提示，不能静默推断业务结论。

产品层负责目录、搜索、业务属性、文档关联、版本导航和阅读状态；引擎负责布局、渲染及已核验的底层交互。不在引擎 Schema 注入任意业务字段，不在 fork 中复制产品目录/权限/搜索逻辑。在线编辑、协作、审批执行和持久化服务属于另立任务，不借初始化扩展实施。

## 3. 版本化产品模型

建议以 JSON 表达产品逻辑源，包含模型版本、流程 ID、不可变修订标识、稳定节点 ID、稳定关系 ID、节点类型/标签、关系起止和业务文档引用。展示标签可变化，ID 不由标签或数组下标生成。跨版本删除/改名需有迁移记录；关系引用失效应拒绝转换。

```json
{
  "schemaVersion": "ordo.flow/v1",
  "id": "sample-review",
  "revision": "example-1",
  "nodes": [
    {"id": "draft", "kind": "step", "label": "准备材料"},
    {"id": "review", "kind": "step", "label": "审阅材料"}
  ],
  "edges": [{"id": "submit", "from": "draft", "to": "review"}],
  "metadataByNodeId": {
    "review": {"description": "合成示例", "documentRefs": ["guide/review"]}
  }
}
```

此示例仅说明职责分离，不宣称已定义完整 Schema。实现时补齐允许类型、大小限制、条件表达、循环规则、文档引用协议与迁移策略。产品元数据和引擎输出通过 ID 映射表关联，转换不能丢失节点/边的可追踪性。

## 4. 适配层与交互容器

拟议目录：`src/model/` 管模型与迁移，`src/adapters/archify/` 管上游转换与调用，`src/reader/` 管阅读体验，`vendor/archify` 是未来固定引擎子模块。当前这些目录与代码均未创建。

拟议契约（伪接口，不是当前可调用 API）：

```text
validate(productModel) -> diagnostics[]
convert(validModel, engineVersion) -> engineInput + stableIdMap + warnings
render(engineInput, pinnedEngine, options) -> htmlArtifact + diagnostics
mapDiagnostic(engineDiagnostic, stableIdMap) -> productDiagnostic
```

校验至少覆盖版本不支持、重复 ID、悬空关系、非法文档引用、无法映射的类型及过大输入。错误携带阶段、可定位的 ID 和非敏感信息；不可支持的语义应报错或明确降级告警，不能静默删除。CLI 调用应传结构化参数，不把用户标签拼入 shell；限制时间、输入规模和输出大小，清理自身临时资源，失败保留上一份可用产物但标明版本，避免把旧图误称最新。

首期建议先验证 CLI 到 HTML 的离线链路，再提供查看入口或 iframe。生成 HTML 视作不可信内容：核转义、脚本能力、外链、CSP 和隔离来源；按最小能力选择 sandbox，不能为交互盲目同时放开脚本和同源访问。未来事件桥接另行定义消息版本、来源/窗口核验、稳定 ID 映射及卸载清理，不假设已有事件协议。

阅读 UI 的 loading、empty、error、success、focus 及不可操作状态需清晰；搜索无结果、生成超时、未知版本、无法加载文档应有恢复入口。键盘导航、焦点、可访问名称、非视觉关系说明及长标签/窄屏布局需要后续真实渲染验证。静态文本或 ARIA 检查不构成可访问性验收。

## 5. 保留历史的引擎 fork 与固定依赖

指定 fork：`RuijinShanhai/archify`，上游为 `tt-a1i/archify`。必须使用真实 fork 并验证 parent、共同祖先与上游历史，不能把下载快照重新 init 成无历史仓或建独立同名替代仓。保留适用许可证、NOTICE、第三方声明和修改标识；通用修复优先回馈上游，等价修复进入上游后验证并撤销本地补丁。

产品与引擎分别管理任务分支、PR、版本和验证记录。fork 中只保留必要补丁，按布局、渲染、底层交互分类，注明原因、原始 SHA、测试和退出条件，避免无限分叉。

计划用 `vendor/archify` Git submodule 固定**完整 40 位提交 SHA**。引擎 PR 验证与集成完成后，产品另开变更更新 gitlink；构建只读取已提交 gitlink，不使用 `--remote` 或随 main 自动漂移。交付应能证明新环境可取得该提交，记录工具链与依赖锁定信息，不能仅因本地缓存可用就称可复现。

当前引擎 fork 未确认创建、版本/许可证未按 SHA 重核，因此这里没有具体 SHA，也没有 `.gitmodules` 或 gitlink。待接入不阻塞产品文档独立发布。

## 6. Agent 辅助升级：审阅与集成独立检查点

每次升级指定上游范围和资源边界，Agent 阅读 release notes、源码差异和测试，并映射产品能力、本地补丁及兼容风险。Agent 提供建议和证据，不自行批准产品需求、合并或上线。

必须分别记录：

|检查点|记录|含义|
|---|---|---|
|已审阅上游|起止 SHA、文档/差异范围、结论与未知、审阅者|只代表该范围已读，不代表采用|
|引擎实际集成|fork 基线 SHA、目标 SHA、merge/cherry-pick/移植映射、PR与测试|证明哪些代码进入引擎，不能只写“跟进最新”|
|产品实际集成|旧/新 gitlink、模型/适配版本、产品 PR、产物与验收|引擎通过不自动等于产品通过|

台账初始三项均为**未建立**，不填写虚构 SHA 或 PR。上游审阅前进可以与实际集成停留在旧版并存，必须保留两个独立游标。

升级优先整版 merge，保留上下游关系；独立修复可 cherry-pick 并记录来源提交；明显分化功能按产品架构移植，记录对应关系和未采纳部分。文本无冲突不等语义兼容，release notes 阅读不代替源码和测试。

## 7. 验证与接受门槛

在任务分支逐层验证，并固定测试输入、工具版本、命令、退出码、日志及产物 SHA：

1. 模型：旧数据迁移、稳定 ID、重复/悬空引用、未知字段/版本、循环与不可达案例。
2. 适配器：节点/关系语义不丢失、诊断定位、不可支持语义、异常/超时与清理。
3. 引擎：中文、长标签、密集关系、分支/循环、布局、路径探索、主题与 HTML 导出。
4. 产品集成：目录/搜索、文档关联、版本导航、容器安全、事件桥（若实施）、错误恢复。
5. 真实渲染：旧/新基线同输入视觉对照、窄屏、键盘/焦点、读屏；自动检查与人工结果分列。
6. 独立评审与测试：未参与实施者核验同一 SHA，CI 与产品验收材料齐备后，由指定集成人串行集成。

本次仅检查 Markdown、暂存差异、身份尾注、秘密特征与仓库分支；没有组件/API测试、引擎测试、构建、浏览器、视觉或读屏结果。没有应用，组件状态覆盖为后续要求而非已测状态。

## 8. 回退与后续交接

引擎升级前保存旧 fork SHA、产品 gitlink、适配/模型版本及合成测试产物。失败时停止晋级，在新任务分支回退产品 gitlink/适配变更并重新验证，不强推或删除公开历史。模型迁移保持旧输入备份和明确逆向/前向兼容策略；代码回退不等数据回退。回退也需 PR 与独立验证，未演练不得宣称恢复能力已证实。

本次文档无运行时或数据迁移；如需撤销已发布方案，按授权用后续 revert 提交保留历史，不清理仓库。开发/测试/生产部署另行授权与隔离，仓库推送不等站点上线。

后续最小交接：补齐 fork 所需 API 认证并核真实 parent/历史 → 按固定 SHA 核许可/测试 → 引擎 PR 与产品 gitlink PR 分别验证 → 最小阅读链路实现。空仓首次只发布任务分支；若 GitHub 自动将其设为默认分支，应只记录真实状态，不擅自推 main 或更改默认分支。没有真实 PR base 时由指定集成方安排基线接收，不能伪造 PR 或以自检替代独验。
